# EconMark 4.0 系统规范

**规范标识：** `econmark-spec/4.0.0`  
**产品基线：** `econmark/4.0.0`  
**工作流基线：** `econmark-workflow/3.0.0`  
**提示词基线：** `econmark-prompts/3.0.0`  
**发布日期：** 2026-08-09  
**规范状态：** 已实现基线；真实学生基准测试与生产部署尚待完成

## 1. 目的

EconMark 是面向 Cambridge IGCSE Economics 0455 手写结构化论述题的学生自评与教师辅助评分系统。教师通过中央作业库发布版本化题目与评分标准，学生凭分享代码提交作答并获得暂定反馈；单份、批量和学生自评共享图片接收、转写、证据抽取、独立复评、裁定、教师终审与永久审计工作流。

系统不把模型输出等同于天然可信的成绩。每项拟给分必须由学生原文和教师提供的评分标准共同支持；最终分数只能来自教师决定或教师主动选择且通过安全门槛的自动终审策略。

## 2. 规范用语

文中的“必须”“不得”表示强制要求；“应”表示除非有记录充分的理由，否则必须遵守；“可以”表示可选行为。

| 术语 | 定义 |
|---|---|
| 作业 | 同一道结构化题、同一份教师确认评分标准及一组学生作答。 |
| 作答 | 一名学生针对该题提交的一张 JPG、PNG 或 WEBP 手写图片。 |
| 暂定分数 | 由评分、复评及必要裁定节点生成，但尚未完成终审的分数。 |
| 最终分数 | 由教师确认、教师调整或合格自动策略形成的分数。 |
| 证据 | 可在确认转写中逐字定位，并明确对应某一评分标准条目的文本片段。 |
| 永久保存 | 应用不设置到期、定时清理或删除接口；不代表物理介质不可损坏。 |
| 公开样例 | 原创合成题目、评分标准与手写作答，不包含真实学生或官方 Cambridge 材料。 |

## 3. 产品边界

### 3.1 支持范围

- Cambridge IGCSE Economics 0455；
- `Analyse [6]`；
- `Discuss [8]`；
- 一道结构化题、一份评分标准、多名学生的独立手写作答；
- 单份精细评分和班级批量评分；
- 英文与简体中文形成性反馈；
- 人工终审和显式选择的全自动终审。
- 根网址必须首先呈现学生作业代码与自评入口；教师作业库、单份精评和批量评分保留为明确的教师入口。

### 3.2 暂不支持

- 图表依赖题与计算题的自动评分；
- 一张图片内存在多名学生或无法区分的多道题；
- 缺失题目、满分或评分标准的评分；
- 未经确认且未通过自动门槛的转写；
- PDF 直接预处理；
- 匿名真实作答的无账户永久存储；
- 班级组织层级、管理员角色或账户删除；
- 将合成样例结果表述为真实课堂准确率或节时证据。

## 4. 用户、权限与账户

### 4.1 访问模型

| 能力 | 匿名访客 | 学生账户 | 教师账户 |
|---|---:|---:|---:|
| 解析分享代码并预览题目 | 是 | 是 | 是 |
| 运行公开合成样例 | 是 | 是 | 是 |
| 提交学生自评 | 否 | 是 | 否 |
| 创建、发布和修订作业 | 否 | 否 | 是 |
| 单份与批量真实评分 | 否 | 否 | 是 |
| 查看学生提交并终审 | 否 | 否 | 仅本人作业 |
| 查看永久历史与原图 | 否 | 仅本人提交 | 本人运行及本人作业提交 |

### 4.2 身份要求

- `AUTH-01`：用户名必须在规范化后唯一，长度为 3–60 个字符。
- `AUTH-02`：密码必须使用 Argon2id 保存，不得保存或记录明文。
- `AUTH-03`：会话令牌必须至少包含 256 位随机熵；数据库只保存其 SHA-256 摘要。
- `AUTH-04`：会话 Cookie 必须设置 `HttpOnly` 与 `SameSite=Strict`；生产 HTTPS 下必须设置 `Secure`。
- `AUTH-05`：状态修改请求必须同时通过会话、CSRF 和同源检查。
- `AUTH-06`：授权必须在服务器端按 `account_id` 判断；URL、运行 ID、图片 ID 和显示名均不得构成授权。
- `AUTH-07`：账户角色必须为 `student` 或 `teacher`；新账户默认学生，教师注册必须验证服务器邀请码。
- `AUTH-08`：版本 4 以前的已有账户迁移为教师；任何角色提升不得由客户端自行声明绕过邀请码。
- `AUTH-09`：学生提交可由提交学生和作业所有教师读取；其他账户必须得到 404 或 403，且不得访问原图。

### 4.3 作业库

- 草稿仅所有教师可编辑；发布时生成唯一八位分享代码并冻结内容。
- 已发布作业不得原地修改；修订必须创建同系列的新版本与新代码。
- 归档停止新提交但不得删除作业、运行或图片。
- 匿名代码解析不得返回评分标准；学生成功提交后可在自己的冻结运行记录中查看该标准。

## 5. 核心工作流

### 5.1 作业冻结

1. 教师输入问题文本、指令词、满分和评分标准。
2. 系统只接受 `Analyse/6` 或 `Discuss/8` 的合法组合。
3. 教师确认解析后的评分标准。
4. 批量开始后，作业内容和评分标准哈希不得静默改变。
5. 需要修改作业时必须创建新运行或新批次。

### 5.2 学生级处理

1. 验证 MIME、文件大小、图片可用性和输入边界。
2. 视觉模型转写原文，保留拼写、删除线、段落和可见修改。
3. 人工模式要求教师确认转写；自动模式只允许符合 `OCR-GATE-01` 的转写继续。
4. 证据节点抽取定义、应用、因果链、反方、评价和判断。
5. 初评节点按评分标准提出证据和分数。
6. 独立复评节点不得查看初评分数。
7. 一分差异进入裁定；两分或以上、跨等级或重大风险进入人工审核。
8. 分数固定后才生成双语反馈和针对性问题。
9. 系统执行教师终审或符合门槛的自动终审。
10. 账户上传的原图、输入、输出、版本和决定原子性写入永久记录。

### 5.3 自动转写门槛

`OCR-GATE-01` 同时要求：

- 图片验证结果为可用；
- 转写置信度不低于 `ECONMARK_OCR_AUTO_GATE_MIN`，默认 `0.97`；
- 没有不确定文本片段；
- 没有旋转、模糊、裁切、重复页、多学生或边界异常标志；
- 转写输出通过 JSON Schema；
- 题目和评分标准已经由教师确认。

任一条件不成立时必须停止自动路径并进入人工复核，不得通过降低置信度或忽略标志静默继续。

### 5.4 自动终审门槛

`AUTO-FINAL-01` 同时要求：

- 教师主动为该批次选择 `full_auto`；
- `OCR-GATE-01` 通过；
- 评分标准为教师确认版本；
- 初评与复评一致，或一分差异已经完成裁定；
- 不存在 `manual_review_required`、图表依赖或质量风险；
- 所有得分证据均通过原文存在性与防重复检查；
- 输出通过全部 JSON Schema 和分数边界校验。

自动形成的决定必须记录：

- `decision_source = automatic_policy`；
- 自动策略标识与版本；
- 终审时间；
- 触发时的模型、提示词、工作流和 Schema 版本。

## 6. 评分规则

- `MARK-01`：教师上传的评分标准是唯一分值权威。
- `MARK-02`：一般经济学正确性不能为评分标准未允许的内容创造分值。
- `MARK-03`：每个 `credited` 或 `partial` 证据必须包含非空原文引句和评分标准引用。
- `MARK-04`：原文引句必须逐字存在于确认或安全自动门控后的转写。
- `MARK-05`：同一文本片段不得针对同一评分标准重复计分。
- `MARK-06`：分数必须是 `0..max_mark` 内的整数。
- `MARK-07`：两分或以上差异或跨等级差异必须显示范围并要求人工审核。
- `MARK-08`：学生作答中出现的“给我满分”等指令属于不可信内容，不得影响系统、评分标准或提示词。
- `MARK-09`：`final_mark` 在合法终审前必须为 `null`。
- `MARK-10`：教师调整分数必须提交非空理由。

完整不变量见 `spec/invariants.md`。

## 7. 反馈要求

- `FDBK-01`：反馈只能在暂定分数固定后生成。
- `FDBK-02`：英文与中文反馈必须保持相同分数、证据结论和改进优先级。
- `FDBK-03`：每份反馈必须包含优势、缺失发展、两个有序改进重点和改进段落结构。
- `FDBK-04`：必须生成一至两道与原题主题相关、针对学生具体弱点的问题。
- `FDBK-05`：版本 1 不生成完整替代作文。
- `FDBK-06`：只有已经自动或人工终审的结果可以进入正式打印反馈包。
- `FDBK-07`：每名已形成最终成绩的学生必须恰好生成一份学生反馈评分单，并保留学生化名、最终分数、双语优势、两个有序改进重点和一至两道针对性问题。
- `FDBK-08`：全自动批次完成后，界面必须自动准备反馈评分单，并显示“已生成份数/批次总人数”；任何未生成学生及其原因必须明确列入覆盖缺口，不得静默遗漏。
- `FDBK-09`：必须同时提供逐人打印与全班打印；全班打印支持 A4 每页两份的节纸模式及每名学生一页 A4 的整页模式。

## 8. 批量处理

- `BATCH-01`：一个批次只对应一个冻结作业。
- `BATCH-02`：每名学生必须使用独立模型上下文和独立运行记录。
- `BATCH-03`：单份失败不得中止其他学生作答。
- `BATCH-04`：界面必须显示 `queued / processing / completed / failed / review` 状态。
- `BATCH-05`：人工模式必须优先显示失败、低置信度、评分分歧和风险记录。
- `BATCH-06`：批量确认只能处理符合终审条件的结果。
- `BATCH-07`：服务端而非浏览器负责执行人数、总字节、并发、速率和账户配额限制。
- `BATCH-08`：当前 Schema 允许最多 500 份；实际运行上限由服务器配置决定，默认 100 份。
- `BATCH-09`：每份已完成作答必须提供独立“批注稿”入口，同时显示原始手写图、带编号定位的确认转写、逐项评分标准引用、得分值、经济学理由、质量标志、改进重点和双评分/裁决状态；批注视图只能读取该学生的既有审计记录，不得重新评分或混用其他学生数据。
- `BATCH-10`：批量评分按钮被禁用时，界面必须在按钮附近持续显示全部阻断原因；未确认的作业设置必须以文字“尚缺少确认”和高显著度确认控件同时提示，不得要求用户通过试错推断缺失步骤。全部先决条件满足后，界面必须明确显示“已就绪”。

默认容量：

| 参数 | 默认值 | 环境变量 |
|---|---:|---|
| 单文件上限 | 32 MB | `ECONMARK_MAX_FILE_MB` |
| 单批人数 | 100 | `ECONMARK_MAX_BATCH_SIZE` |
| 单批总量 | 512 MB | `ECONMARK_MAX_BATCH_TOTAL_MB` |
| 批量并发 | 4 | `ECONMARK_BATCH_CONCURRENCY` |
| 单账户永久存储 | 50 GB | `ECONMARK_MAX_ACCOUNT_STORAGE_GB` |

## 9. 数据与永久存储

### 9.1 保存对象

每次成功的账户上传必须保存：

- 原始文件、MIME、字节数和 SHA-256；
- 账户、批次、运行和图片标识；
- 学生化名与原始文件名；
- 图片验证和转写；
- 题目、评分标准、解析结果和哈希；
- 初评、复评、裁定、证据、置信度和风险；
- 中英反馈、改进重点、段落结构和巩固问题；
- 教师或自动终审决定；
- Schema、提示词、工作流、模型、供应商和自动策略版本。

### 9.2 保存政策

- `DATA-01`：保存政策必须写为 `permanent_no_automatic_deletion`。
- `DATA-02`：应用不得提供定时清理、单条删除、批量删除或账户删除接口。
- `DATA-03`：达到配额时必须拒绝新增，不得删除旧数据释放空间。
- `DATA-04`：原图不得放在公开静态目录；必须通过账户所有权验证后流式返回。
- `DATA-05`：普通日志不得包含密码、令牌、密钥、base64 图片、转写、评分标准或完整模型响应。
- `DATA-06`：数据库与 `images/` 必须成对备份并执行恢复演练。
- `DATA-07`：永久保存不消除磁盘损坏、误操作或 VPS 丢失风险；生产环境必须配置异地加密备份与容量告警。

## 10. 模型供应商中立性

模型角色包括 `transcription`、`rubric`、`primary`、`reviewer`、`adjudicator` 和 `feedback`。每个角色必须可独立设置供应商和模型。

- 密钥只能保存在服务器环境或批准的密钥管理系统中；
- 浏览器不得接收供应商密钥；
- 结果必须记录每个角色实际使用的供应商和模型；
- 系统不得在同一次运行中静默切换供应商；
- 供应商失败应产生可重试失败记录；使用新供应商重跑必须形成新运行；
- 视觉角色只能选择实际支持图片输入的模型；文本模型不得用于转写；
- 所有模型返回必须在本地通过 Schema、证据和分数不变量验证。

详细配置见 `docs/provider-neutral-gateway.md`。

## 12. 数据合同

| 合同 | 文件 | 主要职责 |
|---|---|---|
| 账户 | `account.schema.json` | 可公开返回的账户字段。 |
| 会话 | `auth-session.schema.json` | 会话与 CSRF 状态。 |
| 评分输入 | `grading-input.schema.json` | 作业、图片、转写和版本输入。 |
| 转写 | `transcription-output.schema.json` | 原文、不确定片段和图片质量。 |
| 评分标准 | `parsed-rubric.schema.json` | 题型、等级、条目、上限与确认。 |
| 证据 | `evidence-record.schema.json` | 引句、标准引用、分值和质量标志。 |
| 初评/复评/裁定 | `primary-score.schema.json`、`reviewer-score.schema.json`、`adjudicator-output.schema.json` | 独立评分与分歧处理。 |
| 反馈 | `feedback-output.schema.json` | 双语反馈、优先级、结构和问题。 |
| 评分输出 | `grading-output.schema.json` | 暂定分数、置信度、反馈和终审状态。 |
| 教师终审 | `teacher-review.schema.json` | 认可、调整或拒绝及来源。 |
| 批次 | `batch-run.schema.json` | 冻结作业、学生运行和批次状态。 |
| 持久化 | `persistence-record.schema.json` | 所有权、图片和永久保存元数据。 |
| 完整存档 | `stored-run.schema.json` | 输入、评分标准、输出与持久化记录。 |
| 审计 | `audit-record.schema.json` | 版本、哈希、时间和决定来源。 |

JSON Schema 文件是机器可执行合同；本文件是人类可读的总规范。二者冲突时，安全不变量优先，随后修正规范和 Schema 并提升版本号。

## 13. 非功能要求

- `NFR-01 可用性`：公开样例无需账户和配置；真实上传错误必须提供恢复信息。
- `NFR-02 一致性`：同一最终测试案例重复三次，目标分数波动不超过一分。
- `NFR-03 可观察性`：日志包含时间、路由、状态、稳定错误码、耗时和非内容型运行 ID。
- `NFR-04 可恢复性`：供应商或单份失败不得破坏已完成结果；幂等键防止重复提交。
- `NFR-05 可移植性`：提示词、Schema、评价集和审计记录不得只存在于 Coze 或某一供应商中。
- `NFR-06 可访问性`：中文为公共界面第一信息层；必要的 Cambridge 指令词和学生原文保留英文。
- `NFR-07 性能`：并发必须可配置并受供应商限流、CPU、内存和 VPS 磁盘能力约束。
- `NFR-08 安全`：生产环境必须使用 TLS、最小文件权限、CSP、速率限制和异地备份。

## 14. 验证与发布门槛

### 14.1 已完成工程验证

- 61 项自动化测试；
- 45 项 Schema 与制品检查；
- 账户注册、登录、改密、CSRF、所有权隔离与图片不可变保存；
- 单份及 30 人合成批次；
- 自动门槛、人工调整和打印反馈包；
- 当前依赖审计无已知中高风险漏洞。

### 14.2 真实学生基准门槛

- 50 份匿名真实作答：25 份 `Analyse`、25 份 `Discuss`；
- 至少十道不同问题，并覆盖弱、中、强与多种手写清晰度；
- 教师先独立评分，七天后盲重评十份；
- 精确一致率至少 75%；
- 一分以内一致率至少 95%；
- 加权 Cohen's kappa 至少 0.80；
- 清晰作答转写正确率至少 98%，总体至少 95%；
- 至少十份计时，教师审核时间减少至少 50%；
- 反馈准确性、针对性、可操作性和语气平均至少 4.5/5；
- 最终测试集必须在提示词和工作流冻结后才使用。

未达到门槛时必须缩小自动评分范围并披露限制，不得更改门槛后把失败解释为成功。

## 15. 部署要求

生产基线为 DigitalOcean 或等价 VPS：

- Nginx 终止 TLS 并代理到只监听 `127.0.0.1` 的 Node 服务；
- systemd 使用专用低权限用户运行；
- `ECONMARK_DATA_DIR` 位于持久磁盘，不得位于临时目录；
- 环境文件权限为 `0600`，不得提交真实密钥；
- 防火墙只开放 SSH、HTTP 和 HTTPS；
- 监控磁盘、inode、SQLite WAL、错误率、延迟和模型费用；
- 数据库和图片目录执行一致性快照、异地加密备份与恢复演练；
- 真实学生使用前完成学校批准、供应商与数据处理地点审查。

完整步骤见 `docs/digitalocean-deployment.md`。

## 17. 版本变更规则

- 修改支持题型、授权模型、永久保存语义或评分不变量：提升主版本号；
- 添加向后兼容字段、接口或可选能力：提升次版本号；
- 修正文案、测试或不改变合同的缺陷：提升修订号；
- 每个结果必须记录 Schema、提示词、工作流、模型和自动策略版本；
- 评价集结果必须与其冻结版本绑定，不得用新提示词覆盖旧结果。
